# SynapCores SOAR — Engineer Question Answers

Direct answers to Requirement 12 of the SOAR Demo Completion Requirements doc.

Status as of: synapcores-soar `main` (v0.2.0), against
`synapcores/community:v1.7.0.2-ce-test` engine build.

---

### 1. Which ingestion methods are currently implemented?

See `CAPABILITY_MATRIX.md`. Short answer:

- **First-class CE today:** generic webhook, Splunk HEC, Microsoft Sentinel, CrowdStrike Falcon, Okta event hooks, Slack outbound.
- **Generic-webhook-compatible:** Datadog, Prometheus Alertmanager, GitHub deployment, Jira ticketing, Elastic / SIEM (operator-side schema mapping required).
- **Not yet:** SentinelOne, AWS CloudTrail, OpenTelemetry receiver, Slack inbound — all roadmap for v0.3.0.
- **Enterprise only:** Kafka protocol streaming.

### 2. Is Kafka protocol available in the current enterprise branch?

Yes, in the engine's streaming primitives (`crates/aidb-query/src/streaming_kafka.rs`). The SOAR app's Kafka source adapter is gated to the Enterprise build (feature flag) and not shipped in CE. The demo event simulator includes a `--mode kafka` stub for Enterprise validation but it requires the EE adapter to actually wire end-to-end.

### 3. Do we already support webhook ingestion in CE?

Yes. Generic Bearer-authed `/api/v1/soar/alerts` accepts any JSON payload. Per-tenant connector tokens are minted at `/settings/connectors`. The 4 first-class connectors (Splunk/Sentinel/CrowdStrike/Okta) each have a dedicated route under `/api/v1/connectors/*` with provider-specific normalization.

### 4. Do we have existing connectors for SIEM, EDR, IAM, cloud audit, Jira, and Slack?

| Category | First-class adapter | Generic webhook |
|---|---|---|
| SIEM | Splunk HEC ✅, Microsoft Sentinel ✅ | Elastic, Sumo Logic, Datadog (via generic) |
| EDR | CrowdStrike ✅ | SentinelOne pending |
| IAM | Okta ✅ | Azure AD pending |
| Cloud audit | — | AWS CloudTrail pending (planned for v0.3.0) |
| Jira | — | Generic webhook works for Jira automation rules |
| Slack | Outbound (`notify_channel` action) ✅ | Inbound pending |

### 5. Do we already persist incidents as graph entities?

**Partial.** Incidents are persisted as **rows** in `soar_incidents` with a `soar_incident_alerts` junction. v0.2.0 (this release) adds a **graph projection layer** that mirrors incidents/alerts/users/devices/services into SynapCores' graph store via the dedicated `/v2/graph/*` REST endpoints. The Cypher-from-SQL path (`/v1/query/execute` with `MATCH (n) RETURN n`) is currently NOT wired through the SQL execution context (engine bug #223) — the SOAR app uses the dedicated graph endpoints to avoid this.

See `apps/soar/src/lib/graph/incident-graph.ts`.

### 6. Do we already generate vector embeddings for incidents?

**Yes.** The Tier-1 triage pipeline calls `EMBED(alert.summary || alert.signature)` per-alert and stores the result in `soar_alerts.embedding VECTOR(384)`. v0.2.0 extends this to **incident-level embeddings** — `soar_incidents.embedding VECTOR(384)` is generated by concatenating the constituent alerts' summaries + the analyst-confirmed root cause when the incident closes. This is the embedding the closed-loop learning module retrieves for similar-incident search.

### 7. Do we already support immutable audit verification through VERIFY_CHAIN()?

**Yes.** `soar_audit_log` is a `CREATE IMMUTABLE TABLE` with the SynapCores chain-of-hashes structure. `VERIFY_CHAIN('soar_audit_log')` is exposed in the `/audit` UI as a status indicator and via the MCP examiner portal as a tool. v0.2.0 adds an auto-verify-on-incident-close hook so any tampering surfaces immediately.

### 8. Do agents currently execute actions or only recommend actions?

**Both, gated by HBR (high blast radius).**

- **Auto-executable (no approval needed):** `create_ticket`, `enrich_incident`, `notify_channel`, `attach_evidence`, `mark_related_alerts`, `close_incident` (after RCA approval)
- **Requires human approval before execution (HBR):** `disable_user`, `isolate_endpoint`, `revoke_iam_role`, `rollback_deployment`, `block_ip`

Auto-approve for low-risk actions (Req 6) is implemented in v0.2.0 — the dispatcher checks the action's `risk_level` and the persona's `hbr_actions` allowlist before either executing immediately or enqueueing to `/approvals`.

### 9. Is there an approval workflow already implemented?

**Yes — full `/approvals` queue with approve/reject/modify.**

- Approve → action dispatches via the adapter
- Reject → action is recorded as denied in the audit log
- Modify → analyst edits the action arguments before approving (v0.2.0 addition)
- Auto-approve → bypasses the queue entirely for `risk_level: 'low'` actions on a per-persona allowlist

The HBR-gated set is configurable at `/settings/integrations` per tenant. Approval-latency is captured in the audit log for MTTR metrics.

### 10. What is missing for a complete end-to-end demo?

This release (v0.2.0) closes the gap. After this release, the demo runs **end to end on the published synapcores-soar repo**:

```
alert arrives via webhook
  → triage agent dedups (vector similarity)
  → incident created (row + graph projection)
  → similar incident retrieval (vector + graph overlap)
  → RCA agent produces structured root cause + recommendations
  → analyst approves remediation via /approvals
  → action dispatcher executes via adapter (Slack/Okta/CrowdStrike/etc)
  → audit log records every step (chained hashes)
  → incident closes
  → closed-loop learning saves final state as future memory
  → replay same scenario → previous incident retrieved as similar memory
```

**What still requires the engine to land first:**

- **Cypher-from-SQL** (engine bug #223): the SOAR graph layer uses `/v2/graph/*` REST endpoints as a workaround. When #223 lands, the graph queries can move into SQL directly.
- **AUTOML.PREDICT in CASE WHEN** (engine bug #232): The RCA agent's "recommend action by predicted blast radius" pattern would use this; v0.2.0 splits it into two SQL statements as a workaround.

**Roadmap for v0.3.0 (connector breadth, not closing the loop):**

- First-class Datadog, Prometheus, OTel, GitHub, Jira, SentinelOne, AWS CloudTrail adapters
- Inbound Slack events / slash commands
- Enterprise: Kafka source adapter wired
